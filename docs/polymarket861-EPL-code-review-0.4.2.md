### S1-1 配方摘要和研究纪元的摘要随 Python 小版本变化

**实测** 同一份 0.4.2 源码，同样的 NumPy 2.3.5 和 SciPy 1.17.0，内置 B1 配方的摘要在三个 Python 版本上是三个值：

| Python | 配方摘要 |
|---|---|
| 3.11.18 | `5d2c22a06033c759…` |
| 3.12.3 | `f38b03cee6351d6f…` |
| 3.13.18 | `e9267e19caeb4bf2…` |

配方里各模块的文件摘要和数值库版本在三个版本上是相同的，不同的是 `news_probability_source` 和 `news_frozen_feature_source` 两项。它们由 `news_study_plan._symbol_digest` 和 `news_era_replay._feature_ast` 计算，做法是对语法树的文本表示（`ast.dump`）取摘要，这个文本的格式随 Python 版本变化（读码）。

**影响。** 只升级 Python 小版本、代码一行不改，运行库也会进入 `approval_required`，需要重新比较和具名批准；累计研究会另起一个纪元。开发方公布的两个比较摘要只有在 3.12 下才能复现，我在 3.13 下得到的是 `ab645695…`。仓库的 `requires-python` 是 `>=3.11`，约束文件只固定了依赖包，持续集成三个版本都跑，没有任何文档说明正式运行应该用哪个版本。

**建议。** 在约束文件和升级说明里固定正式运行的 Python 小版本，并把它写进配方。把这两处摘要换成不随解释器变化的算法，例如对选中符号的源码文本做摘要。这件事对五大联赛版本更要紧，见[计划审核](./polymarket861-five-leagues-0.5-plan-review.md)的 P0-4。

**复验。** `check_recipe_digest.py` 分别用三个版本运行，结果在 `recipe-digest-by-python.json`，其中 `parts_that_differ_between_interpreters` 修改后应为空。

### S1-2 公布的“760 场、检出率 79.05%”用的是 0.4.1 的调整幅度

**实测** 处置说明 R2-1 一行写：假定收盘噪声标准差 5 个百分点、斜率 0.5、760 场时，斜率区间的检出率是 79.05%。对应的报告 `reports/news-market-study-0.4.2.json` 记录的输入文件是 `news-early-seals-0.4.1.json`。我用开发方的脚本喂入这份 0.4.1 的封存，输出与发布的报告逐字节相同。换成 0.4.2 自己的封存 `news-early-seals-0.4.2.json`，同一个格子是 17.95%。

原因是 0.4.2 的新闻调整幅度小了一半。十场主胜概率的平均调整幅度，0.4.1 是 1.11 个百分点，0.4.2 是 0.57 个百分点，最大的一场从 2.65 降到 1.02。幅度变小本身是修复 R1-2 的结果：回退不再按最大权重计，多数球员改用真实的出场数据，平均的重要性系数是 0.45。

同一脚本、每格 2,000 次模拟、收盘噪声标准差 5 个百分点时，斜率区间检出的比例：

| 收盘价认可了新闻调整的多少 | 调整幅度取自 | 270 场 | 380 场 | 760 场 |
|---|---|---|---|---|
| 全部（斜率 1） | 0.4.1 | 88.7% | 97.5% | 100% |
| 全部（斜率 1） | 0.4.2 | 23.4% | 40.0% | 77.6% |
| 一半（斜率 0.5） | 0.4.1 | 24.8% | 39.4% | 79.05% |
| 一半（斜率 0.5） | 0.4.2 | 5.8% | 7.6% | 17.95% |
| 没有（斜率 0） | 0.4.2 | 0.4% | 0.2% | 0.5% |

**影响。** 按 0.4.2 的实际幅度，即使收盘价完全认可新闻调整，760 场合格样本也只有 78% 的把握；如果只认可一半，两个英超赛季的样本基本看不出来。达到同样把握需要的样本约为原来的 3.7 倍（推算，幅度的平方之比）。上一份审核稿 R2-1 的表也是按 0.4.1 的幅度算的，表里“回归斜率”几行同样偏乐观，以本表为准。

**建议。** 用 0.4.2 的封存重新生成这份报告并更正处置说明里的数字。研究计划里按新的幅度重新写明预期的样本量。这个结论也影响五大联赛计划里新闻研究的优先级，见计划审核的 P2-2。

**复验。** `developer-script-reruns.json` 的 `reproduce_news_market_study.py` 一段给出两份输入各自的输出摘要和 27 个格子的对照。

### S1-3 以收盘价为参照的研究仍然收不到样本

**读码** 0.4.2 按建议增加了 `scheduled_market_close` 这一档，条件是赛程未变、订单簿满足时限，并且交易所在收盘订单簿前后 30 秒内明确给出 `live=false` 和 `ended=false`（`news_market._state_at_book`）。第一档 `market_close` 需要实际开球证明，而唯一的来源 ESPN 的许可表仍是空的（`kickoff_proof.py`）。处置说明自己也写明，默认接入的合格实际开球来源仍为 0。

**随仓报告** 交易所的这两个标记到现在一次都没有被观察到：0.4.1 和 0.4.2 的采样里没有，五大联赛计划的五场抽样（开球前约 39 小时）里也没有。两档样本在验证副本上都是 0。

**影响。** 如果这两个标记要到开球之后才出现，或者从不以 `false` 的形式出现，第二档就和第一档一样永远是零样本。每过一轮少 10 场。

**建议。** 森林对切尔西是第一次可以实测的机会，收盘采样窗在北京时间 11 月 28 日 03:58 到 04:10。比赛结束后在保存盘口归档的库上运行：

```sql
SELECT live, ended, count(*), min(received_at), max(received_at)
FROM ma_event_states WHERE slug LIKE 'epl-not-che-2026-11-27%' GROUP BY live, ended;
```

如果开球前的记录里没有同时为 0 的一行，建议增加一档“计划开球前收到”的参照，条件和理由写在计划审核的 P0-2 里。

## 5. 其余观察

这几条不影响正式预测，也不急，供开发方排期时参考。

- **S2-1 首发总量的对账只容许少、不容许多。** `news_importance.appearance_totals` 要求队内已列首发总量在应有总量的 90% 到 100% 之间（读码）。曼城和森林的总量仍被拦下，5 条伤停因此回退到 0.55（随仓报告）。如果来源的目录比本机的赛果多算了一场，总量会略高于应有值，现在的规则会一直拦着。建议高出的方向也给一个小的容许范围，并在回退原因里写出两个总量各是多少，现在只能看到“对不上”。
- **S2-2 最新的目录不合格时，不一定会去看上一份。** `directory_players` 从新到旧逐份检查，遇到“首发总量对不上”会继续看更早的一份，遇到“目录时点之前的赛果不全”则直接返回（读码）。后一种情形下更早的目录也可能是可用的。
- **S2-3 伤停持续时间从本机第一次看到算起。** 第 12 轮的 90 条里，持续系数全部是 1.0，因为起点都是 11 月 26 日本机第一次采到的时刻（随仓报告）。球员其实已经缺阵几周时，B1 已经吸收了一部分，这里仍按刚受伤处理。来源如果提供受伤日期，可以用它作起点。
- **S2-4 回归斜率只用主胜一个端点。** 研究计划的斜率是在主胜概率上估的。新闻调整对大小球的影响与对胜平负的影响方向未必一致，加上全场大 2.5 可以多一个独立性较高的端点，代价是校正家族变大。
- **S2-5 停赛按“报道”一档计入，来源字段里没有赛事范围。** 90 条里有 6 条是停赛（Costinha、Mateta、Yeremy Pino、Tarkowski、Igor Thiago、Yoro），缺阵权重都是“报道缺阵”一档的 0.45（随仓报告）。来源的 7 个字段里没有赛事范围，欧战或杯赛停赛与联赛停赛分不开。
- **S2-6 历史重建报告在 3.11 上最后一位不同。** `reproduce_news_history.py` 的输出在 3.12 和 3.13 上与发布的报告逐字节相同，在 3.11 上 1,760 个数里有 8 个在最后一位不同，最大相差 1.4e-14（实测）。原因是内置求和函数在 3.12 改了算法。不影响结论，固定 Python 版本之后自然消失。
