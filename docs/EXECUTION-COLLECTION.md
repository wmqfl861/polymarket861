# 执行簿与历史回补

赛前决策仍使用当时可见的完整比赛目录和决策簿。在执行时段，采集器读取已冻结的正式和影子订单，按比赛、原定开球时刻、原决策截止、合约及其 `secondsDelay` 匹配。多个账本冻结同一方向只请求一次。改期后旧单不占新时段，无冻结单的时段记录为零请求。

一个时段先发一次限时 1.5 秒的小批量 CLOB 请求。1 秒后仍待回执，最多并发补发一次。如果第一份先返回但缺方向，只补缺项。每次都受时段剩余时间约束。时段最迟到计划执行点加 5 秒，以本机收到完整原始响应的 UTC 时间判定。两个及时合格的回执按到达时刻取最早者。每次尝试的令牌列表、真实收件时刻、HTTP 新鲜度、原件 SHA 与耗时可追溯。完整的错误或迟到回执保留原件并单列原因，无响应时记录错误。`season run --execution-research` 可额外请求其他方向，默认关闭。研究请求独立记录为 `books_research`，每进程最多一份在途。这些原始响应不进入执行簿索引。

## 真实采样

2026-11-25 在四场未来英超赛事各选三个公开方向，使用同一进程的持续连接。测量覆盖最后一个响应字节。决策式预热使用最高 12 秒的诊断限时。短请求总限时 1.5 秒。SHA、请求地址、令牌、原始收发时刻和错误均列于逐次记录。[抽样原始统计](../reports/market-collection-0.3.json)

## 回补与限流

逐个时间片先探查细粒度，空结果和实际返回精度都会留下原始收件。任务使用 1 分钟、5 分钟和 30 分钟曲线的最低保留期 7、60、90 天计算哪些数据最早面临丢失。超过最低保留期仍可请求实测。成交、价格和赛事发现轮流获得工作配额。新任务每页最多 1,000 行，已开始的遍历沿用原页长、原过滤器、原游标。服务端 429 或带 `Retry-After` 的 503 对同一主机生效。超过 15 分钟会登记复核时间，原始截止仍有效。[Data API v2 规格](https://data-api.polymarket.com/v2/openapi.json)

实测连续三次分别限 8、40、128 步，每次运行同一个数据目录。赛季目录游标从 150 到 850，再走到末页，累计发现 110 场、4,560 个方向。三批合计索引 42,609 条成交、784 条价格记录，其中 16 条是 `resolution_seconds=0` 的结算点。65 次遍历完成，2 次仍有分页游标，另有 61,718 个价格任务处于待运行状态。已完成批次分别耗时 11.510、24.401、35.493 秒，包含已归档赛事页复用和空粒度探测，不能据此外推整季完成时长。历史行情证据仍没有 A 档或模拟执行收益率。[分批记录与统计](../reports/market-collection-0.3.json)
